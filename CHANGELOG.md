# Changelog

## [Unreleased]

### Added

- **A screen tile lights with up to 256 fixtures, where it was 64.** At 64, a rig of two hundred fixtures had every tile on screen wanting 195 of them and drawing 64 — three quarters of the light an author placed and cued reached nothing, and the scene silently stopped being what it was built to be. Measured before changing it: raising the cap costs what the extra fixtures cost to light and nothing else, with frame time tracking the honest per-tile count almost exactly, so the price is the rig being drawn rather than overhead in the cull. It costs per-tile memory, around 8 MB at 1080p and twice that in stereo. Rigs that never reached the old limit are unaffected in both time and image.

- **Analyse This Scene says when a rig is too dense to draw.** Where more fixtures overlap on one part of the screen than VRSL lights at once, the extra ones contribute nothing and the scene is not lit as it was built — which previously showed up only as a lights-per-tile figure sitting on a round number. The summary now says that some fixtures are not lighting anything from that camera angle, how many reach the same part of the screen against how many are lit, and what to change about the rig.

- **The tile cull now says how much light it threw away.** Each screen tile lights with a limited number of fixtures and the rest were discarded silently — the cull stored the clamped count, so a tile that wanted 200 fixtures and one that wanted exactly as many as it could draw both reported the same figure, and a rig dense enough to lose fixtures looked identical to one that was fine. The count is stored unclamped now and clamped where it is read, so the diagnostics and the benchmark counters report what the scene asked for, how much of it was dropped, and how many fixtures the busiest tile wanted. Nothing about the rendering changes: the same fixtures are drawn, they are just no longer dropped without comment. Benchmark rows also carry the tile grid and the camera whose record produced the figures, because one cull pass serves every camera in a frame and the last record wins — so a tile figure quoted without them is a figure of an unknown view.

- **`VRSL → URP → Validate Renderer Setup`** — reads the active pipeline asset, its renderers and the open scene, and says in one console block what the package needs from the renderer and whether it has it. Which renderer each camera actually resolves to, the rendering and depth-priming modes, whether the depth prepass's layer mask covers the layers the fixtures sit on, and any shader drawing in the opaque queue range without both a `DepthOnly` and a `DepthNormals` pass. That last one is the fault worth a command: with depth priming on, URP draws opaque geometry with an `Equal` depth test against a prepass, so an opaque shader whose depth pass does not reproduce its forward pass is culled from the frame outright — the fixture simply is not there, which reads as a culling or LOD problem rather than a depth one. It checks the package's own shaders and any custom shader sitting on a VRSL fixture, since the second is the one this package cannot fix but can name. **Read-only — it changes nothing**, including the renderer settings, which belong to the project. It reports pass tags, so it can say a depth pass is missing and never that a depth pass which exists reproduces its forward vertex stage; the guides say so where they describe it.

- **`VRSL → URP → Performance`** — a window that answers what the package costs, in milliseconds, in the scene you have open. **Analyse This Scene** needs no setup and no imported sample: it enters play mode, measures the scene at each quality level, and says what turning things down would give back, in the register of "volumetrics are costing 4.2 ms of an 11.0 ms frame, and quality Off returns that" rather than naming a pass or a buffer. It also says whether the scene fits a refresh-rate budget at each level, which is the one field in the window. **Run Standard Sweep** builds its own scene and measures the whole matrix — 10 to 200 fixtures, two camera variants, every quality level — in a single play-mode session, writing a JSON document and a markdown table to a timestamped folder beside the project. **Compare With Baseline** takes two of those runs, matches rows by configuration, and gives each a verdict against the noise floor, refusing to compare across different hardware unless you insist. A scene with no VRSL manager is told so rather than measured.

- **The standard sweep now runs in a built player** — `VRSL → URP → Performance → Build Sweep Player` bakes the sweep's own scene into a standalone build that measures the whole matrix and quits, writing the same JSON and markdown a run from the window does. The reason is the clock: Unity's batch mode reports a GPU frame time of exactly zero, so an unattended capture there is CPU-basis and not a figure anyone should quote, while a player has a real GPU clock and needs nobody watching it. It is the same capture loop the window drives, so the two cannot disagree, and every report says which of them produced it — along with the scripting backend, since CPU-side figures are not interchangeable between Mono and IL2CPP. A player run and an editor run are never compared: the comparison refuses on the difference and names it rather than reporting a delta that is partly the two contexts. The build changes nothing in the project it is made from, and says which Player Setting to turn on rather than turning it on itself.

- A benchmarking API in the runtime assembly — `VRSLBenchmark`, `VRSLBenchmarkRun` and `VRSLBaseline` — for measuring what the package costs in a scene. Cost is measured by difference: the same frames are captured with the managers enabled and disabled, interleaved so drift over the capture moves both sides together, and the package's cost is the gap between the two medians. That is deliberately not a sum of per-pass timings, because Render Graph merges and reorders passes, and because the difference is the figure that matches what an author gets back by turning the package off. Every run records the machine it happened on, the timing source it managed to use, and the package's own counters beside the numbers, so a frame-time change with no counter change is visible as such. Results carry a median and an interquartile range rather than a bare figure, and a comparison refuses to run across different hardware or renderer configuration unless it is forced. Nothing in the light path calls into any of it.

- **`VRSL → URP → DMX Config → Add Basis DMX Record Source (SEI)`** — adds a `BasisUserDataToVRSLDMX` to the selected object and points it at the `BasisMediaPlayer` on it or above it. There is no framing to get wrong on this lane, so it does less than its video-output sibling; what it does carry is the part of attaching it that surprises people. The records win from the moment the component is enabled, whether or not one has arrived, because the manager reads the channel buffer whenever a source is publishing and this one always claims at least `minimumUniverses`. Where the same object also frames a grid, the command says so: on a path that re-encodes the video the buffer stays zeroed and the fixtures go dark rather than falling back to the picture.

- **`VRSL → URP → DMX Config → Add Basis DMX Video Output (Horizontal)`** — adds a `BasisVideoRenderTextureOutput` to the selected object, points it at the RAW DMX grid RenderTexture, finds the `BasisMediaPlayer` on it or above it, and sets the four corner UVs to a transpose. The transpose is the part of the setup that cannot be worked out by eye: the grid RT is 13 cells wide with each row a fixture, while a horizontal grid node's picture is 120 cells wide with each column a fixture, so the two indices swap. A rotation differs from that by a mirror and still fills the RT and still lights the rig while reading every channel off the wrong fixture. Vertical mode is numbered as the RT is and wants no transpose, which is why this is a menu item rather than a change of defaults. The corners it sets transpose the whole frame, which is right as it stands for a stream carrying only the grid; where the grid is a strip inside a larger picture, drag the strip's edges afterwards.

- **DMX Monitor** (`VRSL → URP → DMX Config → DMX Monitor`) — a dockable editor window showing every channel of a universe as a cell shaded by its value, live, from whichever DMX source is driving the scene. It answers what a lit scene hides: whether the values are what the desk sent, which of the two paths the fixtures are really reading, whether a universe has gone quiet, and whether the channel a desk is sending is the channel a fixture is patched at. Three views — VRSL's own 13-wide fixture packing, where a patch off by one shears diagonally rather than reading as plausible colour; a 32-wide desk layout for finding a channel by eye; and an all-universes overview. A `Change` ramp shades by movement since the last sample, which surfaces channel movement a value view cannot; liveness is the per-universe `last heard` figure, since a source republishing unchanged values does not move. Hovering a cell names the universe, channel, flat address and value, and the fixture patched there together with what the channel does for it. An optional Verify mode, on the buffer path only, reads the channels back through the compute shader and compares them against what the source published, which is the existing buffer validation generalised off the synthetic Ramp pattern and onto live data. Read-only throughout: it never writes a channel, so it cannot be the cause of the fault it is used to chase. Play mode only, and nothing runs while the window is shut — a window docked behind another tab parks its sampling and resumes when the tab is shown. Documented in `Documentation~/DMX-Monitor.md`.

- Surface lighting now evaluates a real BRDF instead of adding flat light on top of the frame. A new prepass (`VRSLSurfacePrepass`, driven by the `Hidden/VRSL-URP/SurfaceProperties` shader assigned to `surfacePropertiesShader` on either manager) captures per-pixel albedo, smoothness and metallic into `_VRSLAlbedoTexture` / `_VRSLMaterialTexture`, and the lighting pass runs URP's own `InitializeBRDFData` + `DirectBRDF` against them. A lit surface now keeps its texture colour rather than washing towards white, glossy surfaces pick up a specular highlight, and metals respond as metals. The prepass renders opaque geometry through `DrawingSettings.overrideShader`, so each renderer keeps its own material's property values — URP Lit, Poiyomi URP, lilToon URP and anything else following the `_BaseMap`/`_BaseColor` or `_MainTex`/`_Color` convention contributes with no shader-author involvement. Costs one extra opaque geometry pass; leaving `surfacePropertiesShader` empty skips it and lights every surface as a neutral mid-grey dielectric.

- Screen-space tiled light culling (`VRSLLightCull.compute`, assigned to `lightCullShader` on either manager). A compute pass builds a per-tile list of the fixtures whose range reaches each 16×16 screen tile, and both the surface and volumetric passes iterate that list. Per-pixel cost now tracks lights-per-tile rather than the scene's total fixture count; the volumetric pass benefits most, since its inner loop previously ran the full fixture list once per raymarch step. Tile frusta span the camera's full depth range so one list serves both passes, and tiles are built per eye under single-pass instanced VR. Capped at 256 fixtures per tile. Leaving `lightCullShader` empty falls back to iterating every fixture.

- `DMXFixtureType.StaticPointLight` — a static fixture archetype on `VRStageLighting_DMX_RealtimeLight` that emits as an omnidirectional point light. The manager forces point-light mode for the type and the inspector hides the spot, cone, pan/tilt, gobo, and output-axis fields, so authoring a light bar or par as a point source is a one-pick preset rather than a manual toggle. Runtime behaviour matches a static par with `isPointLight` enabled — the DMX path already carried the point/spot flag end to end, so the type adds authoring ergonomics, not new rendering.
- `use5ChannelMode` on `VRStageLighting_DMX_RealtimeLight` — decodes DMX using the compressed 5-channel static layout (dimmer +0, RGB +1/2/3, strobe +4) instead of the standard 13-channel layout (dimmer +5, RGB +7/8/9, strobe +6), matching the fixture-body surface shader's `_5CH_MODE`. The render-pass light previously only decoded the 13-channel layout, so fixtures patched 5 channels apart cross-talked — each light read its neighbours' channels. The flag rides a reserved slot of the per-fixture GPU config, so there is no buffer-stride change; gobo/spin reads (+10/+11) are suppressed in 5CH since those channels belong to the next fixture.

- `VRSL_URPLightManager` now publishes its assigned DMX grid CRTs as the `_VRSLU_DMX*` shader globals that fixture-body surface shaders sample, so the manager alone drives both the render-pass lights and the fixture-body emissive — `VRSL_LocalUIControlPanel` is no longer required to set those globals for the URP path. A new `dmxStrobeTimerTexture` slot supplies the StrobeTimings CRT (`_VRSLU_DMXGridStrobeTimer`) that the StrobeOutput CRT's decode shader needs to compute the strobe gate. The manager also forces its assigned CustomRenderTextures into Realtime update mode, so it fully replaces `VRSL_LocalUIControlPanel` for the URP path.
- The DMX light manager now derives a fixture's light origin from the centre of the fixture-body mesh it drives (`fixtureShellRenderers[0].bounds.center`) when no `lensTransform` is assigned, before falling back to the component's own transform. This places the light at the lit geometry even when the fixture component sits away from it — e.g. fixtures parked at a shared root while their bar sub-meshes are spread across the scene (common in imported environments where the bars share one transform, so both the component transform and a `lensTransform` pointed at the bar resolve to the root).

- Optional Basis integration (`Runtime/Integrations/Basis/`) that feeds the DMX decode chain from a `BasisMediaPlayer` video stream, so a DMX-over-video signal drives the rig without a capture camera filming a screen quad. `BasisVideoToVRSLDMX` publishes the player's `OutputTexture` as a shader global by reference and republishes only when the texture identity changes, so the native decoder's in-place updates reach the interpolation CRT with no per-frame copy. `BasisVideoRenderTextureOutput` covers the case where the grid occupies part of a larger frame: it blits the player output into the RAW-grid RenderTexture through four source UVs, one per corner, which expresses crop, roll, flip and shear together, and its inspector drags those corners over the live frame (or a still) and can bake a starting point from an existing camera and screen quad. Both fold the player's `OutputFrameIsTopLeftOrigin` into their sampling, so a client whose GPU delivers frames top-left origin decodes the same grid as one that doesn't. The pair compiles into its own `Towneh.VRSL.URP.Basis` assembly, constrained on `com.basis.mediaplayer`; in a project without it the assembly is skipped and the package is unchanged. `com.cnlohr.cilbox` is optional: when present the components are `[Cilboxable]` for sandboxed world scripts, when absent they are plain components for a scene-owned player.

- DMX carried inside the video itself, without a pixel grid. Truss stamps each frame's DMX snapshot into the stream as SEI user data; `BasisUserDataToVRSLDMX` (`Runtime/Integrations/Basis/`) takes those messages from `BasisMediaPlayer.UserDataReceived` as each frame is shown, keeps only Truss's UUID, decodes the record and hands the blocks to the manager as an `IVRSLDMXChannelSource`, so the bytes the desk sent are the bytes the fixtures read. The decoder itself, `VRSLTrussDmx` in the core assembly, is transport-agnostic and verifies the record's CRC and framing before anything is applied: a damaged record is dropped and counted rather than lit. Blocks delivered between two hand-overs accumulate, so a snapshot carrying only the channels that changed loses nothing to a busy frame. The universe count starts at `minimumUniverses` and grows as blocks name higher universes. Setup, the behaviour to expect and the contract for writing a source of your own are in `Documentation~/DMX-Channel-Sources.md`.

- Screen-space contact shadows, off by default via `contactShadowStrength` on either manager. Each light marches the depth buffer from the lit pixel towards the fixture, so an avatar standing in a beam now shadows the floor at its feet. Contact shadowing rather than shadow mapping: only geometry the camera can see, and only within the trace distance — a wall across the room still doesn't block a beam. It's the most expensive term in the lighting loop, which is why it's opt-in.

### Removed

- `RequireDepthLight`, the `_UseDepthLight` property and the `_USE_DEPTH_LIGHT` keyword handling, from the control panel. They existed to work around a Built-in pipeline constraint with no URP equivalent, and the package now states the opposite outright: depth comes from the pipeline, and **no scene light of any kind is needed to obtain it**. Nothing in the package sets a scene up to believe otherwise. The keyword survives in the legacy cone and lens-flare shaders, which are not on the URP realtime path.

- The `Directional Light (For Depth)` prefab, and its instance in all three URP realtime example scenes. It existed to make `_CameraDepthTexture` appear: under the Built-in pipeline a shadow-casting directional light forces the camera to produce a depth texture, which the legacy volumetric mesh shaders sample for their depth fade. URP has no such coupling — the depth texture comes from the URP Asset's Depth Texture setting or from a pass calling `ConfigureInput`, which every VRSL pass that reads depth already does. The light was contributing nothing, and because it shipped with hard shadows enabled it was drawing a main-light shadow map every frame for a light whose colour is black at 0.001 intensity, which is exactly the per-light shadow cost the URP light path exists to avoid. **If you copied this prefab into your own scene, delete it** — depth still works without it, verified with no lights in the scene at all.

### Changed

- The AudioLink moving-head fixture meshes declare their own `DepthOnly` and `DepthNormals` passes rather than taking URP's Lit ones through `UsePass`. Borrowing Lit's was safe only because the AudioLink branch of the shared vertex include has its pan and tilt rotation commented out, so the borrowed depth pass happened to agree with the forward one. Anybody re-enabling AudioLink pan and tilt would have broken both shaders under depth priming, and the symptom — a fixture body that vanishes — reads as anything but a depth problem. The new passes share the forward fragment program deliberately: the requirement is about the vertex stage matching exactly, and reusing the whole program guarantees that by construction rather than by inspection, while carrying the alpha clipping this queue needs.

- The three URP example scenes ship with their non-URP fixtures switched off. Flashers, lasers, light bars, multi-light bars, the 6x4 strobes, the discoballs and the example surface shader were carried through from the Built-in package and never given URP variants — they are the prefabs outside the `*-URP-Fixtures` folders, and they still carry dead VRChat-Udon script slots that no URP fixture has. Disabled rather than deleted, so their transforms and DMX patch survive for whenever each is ported. The discoball is the one that mattered most: in its low quality mode it draws opaque and writes depth with no depth pass, so depth priming culls it outright.

- Surfaces hidden by a shader's own visibility logic no longer pick up VRSL light through the wrong albedo. The albedo prepass draws through `DrawingSettings.overrideShader`, which replaces the material's shader outright, so anything that decides visibility inside that shader never runs — Poiyomi's UV Tile Discard being the case that surfaced it. In its default Vertex mode Poiyomi returns NaN from its vertex program, collapsing the triangle in the passes that feed `_CameraDepthTexture`, but the prepass still drew the geometry; the lighting pass then took its position from the camera's depth (the surface behind) and its albedo from the prepass (the discarded avatar), so the hidden shape reappeared as lit colour. The prepass now publishes its depth as `_VRSLSurfaceDepthTexture` and the lighting pass ignores albedo wherever that disagrees with the camera's depth, falling back to the neutral dielectric it already uses for surfaces with no prepass data. Compared in linear eye space against a tolerance proportional to viewing distance, since the two depths come from different compilations of the same transform and so agree closely rather than exactly. Also covers custom alpha clips and vertex displacement, which had the same mismatch for the same reason.
- `volumetricStepCount` defaults to 24 rather than 32, on both managers and all four URP light-manager prefabs. Now that each light's span is bounded to its cone, every step lands inside the beam, so the same visual quality needs fewer of them — 16 held up on a rig of 60° spots at 20 m range. Scenes that set the field explicitly are unaffected. What governs the floor is metres of cone per step rather than the count alone, so wide cones, long beams and dense haze still want more.
- Volumetric cones no longer show structured stepping. Each light is marched across the part of the view ray that falls inside its cone, found by intersecting the ray with the light's bounding sphere and then narrowing that to the cone via `VRSL_NarrowSpanToCone`. Marching the sphere alone spends the step budget mostly outside the beam — at a 20 m range the chord runs to 40 m and includes the whole backward hemisphere, while a ray crossing a beam near the lens covers well under a metre of lit space — so a handful of samples carried the whole result. That is quadrature error large enough that the dither can't conceal it, and it surfaced as whatever pattern the dither carried rather than as fine grain, worst near a fixture head where the cone is narrowest relative to its sphere. Point lights fill their sphere and keep the sphere span. Because the span is now tight, `volumetricStepCount` can usually go well below its default before stepping is visible.
- The half-res volumetric upsample reconstructs smooth gradients correctly. Taps were centred on the nearest half-res texel, so all four full-res pixels of a 2×2 block resolved to identical taps and weights and the composite was constant across the block, which terraces a gradient into contours. Weights now follow the pixel's true sub-texel position through a separable tent of radius 1.5, chosen so a tap reaches zero weight as the centre texel flips and the reconstruction stays continuous. The depth term is also fixed: it weighted by `1/(eps + depthDiff)` with `eps` as a divide guard rather than a tolerance, which is unbounded near zero and gave the centre tap a weight orders of magnitude above its neighbours on any non-fronto-parallel surface, collapsing the 3×3 kernel to a point sample. It is now `1/(1 + d²)` against a tolerance proportional to viewing distance.
- The raymarch step dither is interleaved gradient noise rather than a Weyl lattice. `frac(a*x + b*y)` has straight diagonal iso-value contours, so every pixel along one diagonal received an identical step phase and residual stepping streaked into a diagonal weave instead of breaking up. Same cost.
- The volumetric raymarch integrates each light across the span of the view ray that falls inside that light's own range, instead of every light sharing one march from the camera to the opaque surface. A shared march sizes its steps against whatever geometry happens to sit behind a beam, so a cone a few metres from the camera with a distant wall behind it drew one or two samples out of the whole budget, and the jitter that hides banding turned that undersampling into the grain that made `Half` read as dithered. Sample density now follows the beam's own thickness and is independent of scene depth, which is where the visible improvement at `Half` comes from. The per-light budget is the full `volumetricStepCount`, so the worst case costs what the shared march cost; rays that miss a light's bounding sphere now skip it for a few ALU rather than stepping through it, so scenes whose fixtures don't fill the frame get cheaper. With `volumetricUseNoise` enabled the density noise is sampled per light rather than once per shared step, costing a fetch per light per step wherever cones overlap.
- `VRSLLightData` is 64 bytes rather than 80, cutting the buffer traffic of the volumetric inner loop by a fifth. The active flag is gone — a fixture emitting nothing is written with zero intensity, which the readers already had to check — and the light type and gobo slice share `directionAndType.w`. Both packed values are small integers, which floats represent exactly, so nothing loses precision; packing them as halves would have quantised the gobo spin phase and stippled a slow rotation. Shaders read them through `VRSL_LightType`, `VRSL_GoboIndex` and `VRSL_IsActive` in `VRSLLightingLibrary.hlsl`.
- **Breaking:** a DMX fixture at full output is now half as bright. `maxIntensity` is defined as being on the same scale as a URP spot light's Intensity value, which requires the dimmer curve to reach exactly 1 at full DMX. It previously peaked at `curveMod` — 2 on the default curve — so a DMX fixture emitted twice what its `maxIntensity` said, and twice what an AudioLink fixture set to the same number emitted. The curve's shape is unchanged, so the cast light still ramps together with the fixture-body glow. To restore previous brightness, double `maxIntensity` on affected fixtures, or set `curveMod` to 1.
- The gobo wheel is packed on the GPU. `BuildGoboArray` previously did a `ReadPixels` readback and a CPU upload per slot, stalling whenever fixtures were refreshed, and resampled every gobo to 256². Slices are now blitted straight into an array render texture at the resolution of the largest source (clamped to 1024).
- With both the DMX and AudioLink managers active, the surface prepass runs once rather than twice. Its output doesn't depend on which manager drives it, so the DMX manager owns it and the AudioLink manager defers. Saves two opaque geometry draws per camera in dual-manager scenes.

- `VRSLNormalsPrepass` is now `VRSLSurfacePrepass`, since it captures albedo and material data alongside the authored normals. The normals half is unchanged — same `DepthNormals` / `DepthNormalsOnly` shader tags, same `_VRSLNormalsTexture` global.
- Both light passes skip the gobo texture fetch wherever a light already contributes nothing, and the surface evaluation rejects lights outside their range before doing any further work. The gobo fetch is the most expensive part of either inner loop, and a gobo can only ever reduce a light's contribution.

- Package identifier renamed from `net.towneh.vrsl-urp` to `town.mr.vrsl-urp`. All `Packages/net.towneh.vrsl-urp/...` shader include paths and editor/runtime asset-path constants follow the new name. Consuming projects need their manifest entry key updated to `town.mr.vrsl-urp`; local `file:` paths and asset GUIDs are unaffected.
- The DMX screen-reader prefabs (horizontal and vertical) no longer carry a `MeshCollider` on the screen quad, and the quad no longer samples light probes. The control panel prefab has been stripped of the two leftover UdonSharp behaviours it inherited from upstream, along with the button events that targeted them.

### Fixed

- The three DMX light-manager prefabs now ship with their strobe timer texture assigned. The field arrived after those prefabs were last saved, so it deserialised as empty in every scene built from them — and empty is only safe in a scene that never strobes. The StrobeOutput CustomRenderTexture's decode shader samples that texture to work out the strobe gate, so where strobe was used the whole rig could go dark rather than merely stop flashing, with nothing in the Console to say why. Scenes that already assigned it by hand are unaffected. Re-saving the prefabs also wrote out fourteen fields that had been left implicit — contact shadows, strobe frequencies, movement smoothing and the rest — each at the value the script already defaulted to, so nothing else about them changed.


- A light manager that is switched off in the inspector no longer takes the singleton and stops the running one from working. `Awake` runs on a disabled component whose GameObject is active, while `OnEnable` and `OnDisable` never do, so a claim made there was never released: the manager that was actually running found the singleton taken, destroyed itself as a duplicate, and the scene lit nothing with no error in the Console. Neither manager now claims it until it is enabled, and both release it when they are switched off again. Affects any scene carrying a spare manager parked switched off.

- `VRSL_AudioLinkURPLightManager` re-claims the singleton when it is enabled, so a manager switched off and on again keeps working. `Awake` claimed it and `OnDisable` released it, but `Awake` does not run a second time, so the component's `Instance` stayed null for the rest of the session and every render pass silently early-outed — the AudioLink light path stopped with nothing in the Console to say why. The DMX manager already did this; the two now behave the same way.

- The VRSL logo is back at the top of every inspector that draws the package header. It was loaded through `Resources.Load`, which only ever searches folders named `Resources`, and the package's one copy of the logo does not live in one, so the lookup returned null and each of those inspectors reserved a blank 140-pixel strip instead. It now loads by asset path, with a search by name behind it so an embedded or relocated copy of the package still resolves, and a header with no logo to draw takes no space at all.

- `BasisVideoRenderTextureOutput` no longer curves the DMX values it frames. In linear colour space the sampler converts an sRGB source and the writer converts back only for an sRGB target; the player's desktop output texture is sRGB and the RAW grid RenderTexture is linear, so every channel arrived gamma-encoded and far too low — a value of 104 read as 35, and 104 and 105 both landed on 35, which no downstream correction can undo once it is written at eight bits. The blit now re-encodes its sample while the value is still float, and only where the two formats actually disagree, so the Android path (whose player output is already a linear RenderTexture) is untouched. Affected the DMX-over-video path only; a picture output was always correct, which is why the conversion is right for those and wrong for this one.

- DMX channels past the second in each grid row decoded from the row below. The Built-in path passes its computed row through `IndustryRead(int x, int y)`, truncating it to an integer before scaling into UV; the URP compute port kept the division but dropped the truncation, leaving `frac(channel / 13)` of a row of drift. The inherited `-0.001915` offset absorbed about 0.23 of a row, so the first couple of channels in each row and the exact multiples of 13 kept working while most per-fixture offsets — dimmer at +5, colour at +7/8/9 — read a neighbouring fixture's value, decoding plausible numbers rather than failing visibly.

- A DMX fixture whose colour faded to black while its dimmer stayed up kept visibly emitting: the light's active flag was gated on decoded intensity alone, and the residual near-black RGB got amplified by `maxIntensity` — for point lights whose origin sits on the bar mesh, by strong near-field attenuation too. The flag now also requires a colour channel above `6/255`, which clears the fade residual even at high `maxIntensity`, at the cost of clipping colours dimmer than ~2.4%.
- DMX fixture-body surfaces decoded a black grid while the render passes were active. The grid CRTs were published with `Shader.SetGlobalTexture`, which URP's render graph binds to scene shaders as a 1×1 black fallback — every bar and par surface stayed dark even though the render-pass lights, whose compute binds the CRTs directly, kept working. The compute pass now re-publishes the CRTs via `SetGlobalTextureAfterPass` so the opaque pass samples the live textures. The surface decode also now samples through an explicit point/clamp sampler (a CustomRenderTexture's runtime filter mode frequently resolves to Bilinear regardless of the asset setting, bleeding neighbouring channel cells into the read) and takes its texel size from the manager-published `_VRSLDMXTexelSize` global rather than the texture's auto `_TexelSize`, which Unity overwrites for globally bound textures; the resulting row-UV drift grew down the grid, so the highest-patched fixtures decoded the wrong (often black) cell.
- DMX **point-light** fixtures (`isPointLight` / `StaticPointLight`) were silently masked to near-zero whenever the manager had gobo textures assigned. The compute clamped every fixture's gobo to slot 0, and `SampleGobo` then projected it as a spot cone — returning 0 for the spill behind the light axis and multiplying the front by the (often dark) slot-0 texture. Point lights now keep `goboIdx = -1` (the `SampleGobo` no-op), so their omnidirectional spill is unmasked and scales with intensity as expected. Symptom was a large decoded intensity with no visible scene spill that didn't respond to `maxIntensity`.
- The URP `VRSL_LocalUIControlPanel` custom inspector aborted every repaint with a `FileNotFoundException` because `GetVersion()` read a `Runtime/VERSION.txt` the package never shipped. The throw happened before `base.OnInspectorGUI()`, so none of the panel's serialized fields drew — the CRT source arrays (`DMX_CRTS_Horizontal` etc.) looked empty and couldn't be wired, leaving the `_VRSLU_*` DMX globals unpublished and fixture-body surfaces unlit. `GetVersion()` now guards the read with `File.Exists` and a try/catch fallback, and the package ships `Runtime/VERSION.txt`.

### Known issues

- **Par, blinder, laser, and discoball fixture meshes do not render correctly under single-pass instanced VR.** The mesh body / projection geometry on these fixture types is missing or misplaced in one or both eyes. Moving heads (spots and washes) and the surface lighting and volumetric-cone passes are unaffected. A previous fix (`1746a30`) addressed the same class of issue for the moving-head body / volumetric meshes by routing their shaders through `#pragma multi_compile _ STEREO_INSTANCING_ON STEREO_MULTIVIEW_ON` and making their `DepthOnly` / `DepthNormals` passes SPSI-aware; the par, blinder, laser, and discoball shaders still need the equivalent treatment.

## [0.1.0] — Initial release

### URP Realtime Lights — Unity 6 / URP 17+

The pipeline is four Render Graph passes — all reading the same per-fixture GPU buffer — injected at runtime by the manager MonoBehaviour via `RenderPipelineManager.beginCameraRendering`. No URP Renderer Features required, no URP asset / renderer asset settings touched by the package; co-exists with whatever rendering path, MSAA setting, depth-priming mode, and depth-texture configuration the project uses.

A VRSL-owned normals prepass renders opaque scene geometry with the standard URP `DepthNormals` / `DepthNormalsOnly` shader tags into a VRSL-owned RT, so authored surface normals from any URP-targeted shader (URP Lit, Poiyomi URP, lilToon URP, Mochie URP) come through automatically — avatars and props receive smooth-shaded VRSL light without their authors needing to add anything URP-specific.

- **Compute** decodes per-fixture state (position, direction, colour, intensity, cone, gobo) into a `StructuredBuffer`.
- **DMX** — `VRStageLighting_DMX_RealtimeLight` + `VRSL_URPLightManager`. Decodes the existing CRT chain on the GPU; no per-frame CPU cost per fixture.
- **AudioLink** — `VRStageLighting_AudioLink_RealtimeLight` + `VRSL_AudioLinkURPLightManager`. Reads animated transform directions on the CPU each frame and samples the global `_AudioTexture` on the GPU. Per-fixture color modes include emission, theme colors, ColorChord, and ColorTexture sampling against an optional scene-wide `samplingTexture` on the manager.

URP fixture prefab variants ship as standalone — the Realtime light is the sole authoring surface and drives the fixture body emissive directly via `fixtureShellRenderers`. Volumetric controls (resolution mode, modulated 3D-noise density, scene-fog coupling) and per-fixture controls (`emitterDepth`, `globalIntensity`, `targetToFollow`, `lensTransform`) are exposed on the manager and Realtime light inspectors. See `Documentation~/URP-Realtime-Volumetric-Lights.md` and `Documentation~/URP-Fixture-Configuration-Guide.md` for details.

Editor menu utilities:
- **VRSL → URP → Add Light Manager to Active Scene** drops a configured manager into the active scene with compute / lighting / volumetric shader references assigned.
- **VRSL → URP → AudioLink Config → Setup AudioLink Realtime Lights in Scene** configures every AudioLink mover spotlight in one click.

### Package origin

Extracted from the `urp-volumetric-lights` development branch on towneh's fork of `com.acchosen.vr-stage-lighting`, then refactored as a coexisting URP overlay package so the URP path can ship and evolve independently of the upstream VRChat-targeted package.

### Coexistence with com.acchosen.vr-stage-lighting

Standalone — no dependency on `com.acchosen.vr-stage-lighting`. The fork carries its own copies of the CRT DMX decode chain, fixture meshes and shaders under distinct asset GUIDs, shader namespaces (`VRSL-URP/…`), C# namespaces (`VRSL.URP`) and runtime globals (`_VRSLU_DMX*`), so it installs alongside the upstream Built-in-pipeline package without collision. That coexistence exists to make BIRP → URP migration incremental: both packages can run their own fixtures in the same project while a scene is moved across. Existing upstream scenes and prefabs continue to work alongside; this package never replaces upstream assets.
